## 问题 1：eventType 命名规范

**回复：以小写 `ask_doubt` 为准。** ✅ 你当前用的就是正确的。

文档中的 `STUDY_SESSION_END` / `COURSE_COMPLETED`（大写下划线）是旧示例，M6 v1.0 契约定义的 10 种事件类型全部使用**小写 + 下划线**格式：

```
answer_question, finish_practice, request_explanation, explanation_feedback,
weak_point_changed, lecture_interact, lesson_material_used, ask_doubt,
mark_reviewed, preference_changed
```

`event_collections` 表的 `eventType` 字段写入 `"ask_doubt"` 即可，不需要改。

## 问题 2：confusionTag 怎么获取

**回复：当前固定 `concept_unclear` 占位可以接受。** ✅

原因是 M6 引擎对困惑类型的判断分为两步：

1. **优先**用正则从 `topic` 原文匹配（5 种正则模式，中英文均可识别），命中后返回对应中文标签
2. 正则未命中时，才用 `confusionTag` 作为 fallback，映射到对应中文

所以你传 `concept_unclear` 作为兜底是合理的——大部分有意义的提问会被正则命中，confusionTag 只在学生问得特别模糊（如"这题怎么做"既可能匹配"方法不理解"也可能匹配不到）时起作用。

**后续建议**（非阻塞）：如果 M7 侧后期有条件让 AI 在生成回答的同时输出困惑分类（从 concept_unclear / formula_confusion / step_unclear / application_difficulty / careless_error 中选一个），会比固定值更精准。但这不是当前必须做的。

## 问题 3：触发时机

**回复：当前策略合理，无需修改。** ✅

具体来说：
- **一次完整问答（拿到完整回答）→ 上报** ✅ 正确
- **缓存命中秒回 → 上报** ✅ 正确（学生确实完成了提问并得到了答案，算一次学习行为）
- **打断 → 不上报** ✅ 正确（没有形成完整学习行为）
- **出错 → 不上报** ✅ 正确

**唯一补充**：缓存命中秒回时，如果 `isFollowUp` 能正确反映"同一会话内是否已有历史提问"就更好了。比如缓存命中的首问应该 `isFollowUp=false`，后续追问才为 `true`。如果技术上不太好区分，固定策略也 OK，对画像影响有限。

## 问题 4：topic 截断到 120 字

**回复：可以接受。** ✅

M6 契约要求 topic 去除首尾空白后 1-120 个 Unicode 码点。超过 120 字后截断不会影响正则匹配效果——困惑检测的模式（"为什么"/"不懂"/"什么意思"等）通常出现在前几十个字以内。截断到这个长度也足够引擎做判断了。

建议截断逻辑：**取前 120 个 Unicode 码点**（不是 120 个字符/字节），与 M6 的 `len(topic) > 120` 校验保持一致。

---

## 问题 5：是否只需上报 ask_doubt

**回复：当前只需要 `ask_doubt`。** ✅

`STUDY_SESSION_END`（会话结束）等事件不在 M6 v1.0 的 10 种事件类型中，M6 引擎暂时不需要。如果后续需要对话时长等维度，届时再约定新增事件类型。

---

## 问题 6：上报走本地写入还是 HTTP 远程

**回复：本地直写 `event_collections` 表即可。** ✅

当前 M7 与事件采集服务同一后端部署，直接写表与 M2 一致，是最简单的方案。文档中标 `http://192.168.1.19:8080` 是给前端或独立部署模块用的 HTTP 入口，后端模块可以跳过这一层。

`event_collections` 表写入后，网关层（吴敏希负责）会统一读取 `processed=0` 的事件、转换 v1.0 格式、调用 Python 引擎。
